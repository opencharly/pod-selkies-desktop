## Why this pin is being advanced a fourth time

`v2026.243.1051` → `1744` → `1811` → `1844` across this campaign. Each value was newest when it
landed, and `pod-selkies-core` was itself being repaired in parallel, so every fix downstream
re-staled this pin.

That is the defining property of repairing a pin graph whose leaves are still moving, not churn to
apologise for — and it is why the closure is **re-measured between waves** and the introducer chain
**re-derived each round** rather than predicted once. Twice in this campaign a predicted chain was
wrong by the time the wave landed; only the re-derivation caught it.

## Why it cannot be fixed downstream

The consuming project cannot clear it: the stale pin lives inside **this** repo's published tag,
not in theirs. `charly box reconcile` there rewrites only that project's own pins and reports no
change against this warning.

## The candy's own `version:` is deliberately NOT bumped

`PickCandyVersion` (`sdk/loaderkit/candy_version.go`) warns only when two materializations of a
bare ref carry **different per-entity `version:` values**; identical entity versions across
different git tags resolve silently on tag freshness. Bumping the stamp for a pin-only change
would manufacture the exact warning this PR removes, for every consumer still pinning an older tag
of this repo.
