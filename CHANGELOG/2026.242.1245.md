# 2026.242.1245 — fix: advance to the repaired pod-selkies-core, migrate schema, repin CI charly

## Summary

Advance `pod-selkies-core` from `v2026.240.2344` to `v2026.242.1242`, and move this repo's schema
and CI charly pin so the change can actually be gated.

**What the advance carries — two things, both load-bearing.**

**1. The `plugin-wl` advance finally reaches the corpus.** `opencharly/pod-selkies-core#6` and
`layer-sway-desktop-vnc#3` both advanced their `plugin-wl` pins, but consumers reach `plugin-wl`
*through this candy*, and this candy still pinned the pre-advance core. So the old version stayed
in the graph and charly reported two:

```
Warning: candy .../plugin-wl resolved to multiple versions;
         using newest 2026.242.0600 (from …@v2026.242.0610), ignoring 2026.187.1200 (from …@v2026.237.1430)
```

Measured at the two core tags, which is where the difference actually lives:

```
pod-selkies-core@v2026.240.2344  ->  plugin-wl:v2026.237.1430     (the stale side)
pod-selkies-core@v2026.242.1242  ->  plugin-wl:v2026.242.0610
```

`plugin-wl v2026.242.0610` brings **B3's compositor capability table**. Measured on
`check-selkies-labwc-pod` over the same 212 steps, that advance turns **43 failures into passes**:

```
plugin-wl v2026.237.1430:   212 steps: 139 passed, 55 failed, 18 skipped
plugin-wl v2026.242.0610:   212 steps: 182 passed, 12 failed, 18 skipped
```

The schema change is purely additive — six `hypr-*` methods added, nothing removed or renamed — so
every step this candy authors keeps its exact meaning.

**2. It closes the bare-name candy chain.** `v2026.242.1242` is the tag from `pod-selkies-core#7`,
which advanced four pins that reached candy tags referencing `pixi` and `plugin-record` by bare
name (both became separate repos in the candy cutover). That chain was landed leaf-first beneath
this PR: `pod-selkies#4` → `layer-wl-record-pixelflux#4` + `layer-wl-screenshot-pixelflux#3` →
`pod-selkies-core#7`. This branch originally reached for `v2026.242.1155`; `v2026.242.1242`
supersedes it and is the first core tag that resolves clean.

**Why the schema and CI pin move.** `charly box validate` — the gate for this change class —
refuses to run until the schema is migrated:

```
schema 2026.240.1943 is required (found "2026.232.0520"). Run: charly migrate
```

and the migration is precisely what makes the CI's pinned charly too old:

```
config schema 2026.240.1943 is newer than this charly supports
```

Landing either half alone leaves the repo broken in one direction or the other.

### 3. Why `CHARLY_PLUGIN_ONLY=1` — RCA, not a dismissal

Run without it, this gate emits one warning, and it is charly's own deliberate signal, so it gets a
root cause. `plugin_loader.go:434 warnSkippedFHSPlugins()` fires when the running binary is not at
`/usr/bin`/`/usr/local/bin` **and** `/usr/lib/charly/plugins` holds `.providers` manifests. Its own
comment gives the intent: those plugins *"were built against a different charly version (issue
#328)"*, so a dev binary must not load them, and the warning makes the skip visible instead of
silent.

```
(a) What would have been loaded:  /usr/bin/charly version -> 2026.187.2228
    …against a tree requiring schema 2026.240.1943 — 55 days and a schema epoch apart.
    Refusing to load them is CORRECT; loading them would be the defect.

(b) Caused by this PR? No — it fires identically on an untouched clone of main.

(c) Does the skip weaken this gate? Provably not. plugin_loader.go:454 documents
    CHARLY_PLUGIN_ONLY=1 as "the supported way to resolve AS-IF-UNPACKAGED" — it DROPS
    the FHS path from the search, masking nothing, and its output is byte-identical to
    the normal run minus that one line.
```
