# 2026.243.1826 — chore(deps): advance pod-selkies-core to current

## Summary

One pin, and it is the tail of a cascade:

```
-            - '@github.com/opencharly/pod-selkies-core:v2026.243.1744'
+            - '@github.com/opencharly/pod-selkies-core:v2026.243.1811'
```

A published tag embeds the pins it carried **at mint time**, and this repo's tag is what
consuming projects fetch. `pod-selkies-core@v2026.243.1744` still pins an older `pod-chrome-cdp`
and `pod-selkies`, so any closure that reaches `pod-selkies-core` *through this repo* inherits all
of it — even though `pod-selkies-core` itself has since been fixed and re-tagged.

**Three of the four conflicts remaining in a consuming closure trace through this single link**,
established by walking that closure's transitive ref graph (590 pinned refs) back to the tag that
introduces each stale version:

```
pod-chrome-devtools-mcp:old <- pod-chrome-cdp@old <- pod-selkies-core@1744 <- THIS REPO
layer-cuda:old <- layer-supervisord@old <- pod-chrome-cdp@old <- pod-selkies-core@1744 <- THIS REPO
pod-selkies:old                          <- pod-selkies-core@1744 <- THIS REPO
```

`pod-selkies-core@v2026.243.1811` already carries current versions of all three, so advancing this
one pin clears them together.

## Why this pin is being advanced for the third time

`v2026.243.1051` was newest when the first repin landed; `v2026.243.1744` when the second did.
Each was superseded within the hour by `pod-selkies-core`'s own re-tag, so the earlier PRs became
the next wave's stale link.

That is inherent to repinning a moving target rather than an error to avoid: a repin is only
current relative to when it lands. It is why this campaign repairs the graph **leaves-first and
re-measures the closure between waves** instead of planning one pass — and why the introducer map
is re-derived each round rather than reused, since it demonstrably moves.

Progress measured in the consuming closure, each figure taken after the preceding wave's tags
landed:

```
12 conflicts -> 6 -> 5 -> 4    (this PR targets 3 of the remaining 4)
```

The replacement tag was confirmed to exist before pinning:

```
$ git ls-remote --tags --refs https://github.com/opencharly/pod-selkies-core | grep v2026.243.1811
```

The effect is only observable in a consuming closure — that is where two materializations of a
candy meet and `PickCandyVersion` picks between them — so that is where it was measured, with a
stock `task build:binary` charly.

**On runtime risk:** charly's arbiter selects the newest per-entity version across the *whole*
closure, so consumers composing this candy alongside anything current were **already executing**
the newer `pod-selkies-core`. This pin makes the declaration match what was already running rather
than introducing an untested version.

## The candy's own `version:` is deliberately NOT bumped

`PickCandyVersion` (`sdk/loaderkit/candy_version.go`) warns only when two materializations of a
bare ref carry **different per-entity `version:` values**; identical entity versions across
different git tags resolve silently on tag freshness. Bumping the stamp for a pin-only change
would therefore manufacture the exact warning this PR removes, for every consumer still pinning an
older tag of this repo.
